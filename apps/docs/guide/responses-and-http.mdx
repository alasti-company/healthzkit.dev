## Rollup status

Overall `HealthResponse.status` is computed from all check results for that probe:

1. Any **`fail`** → **`fail`** (unless remapped by `onFail.treatAs` on that check).
2. Else any **`degraded`** → **`degraded`**.
3. Else **`ok`**.

Override with `rollup.computeStatus(results)` for custom rules.

## HTTP status

Response **`status`** (HTTP code) is derived from the rolled-up health status and your config:

- Any check with **`status === "fail"`** and **`onFail.httpStatus`** set → that value is returned (first matching check in config order wins among failed checks with a custom status).
- Else if rollup is **`fail`**: `defaults.onFail.httpStatus` or **503**.
- Else if rollup is **`degraded`**: the first check in config order with **`status === "degraded"`** and **`onDegraded.httpStatus`** set wins. If none matches, use `defaults.onDegraded.httpStatus` or **200**. A degraded override never takes precedence over a failed rollup.
- Else **200**.

`onFail.treatAs` changes the **check** status before HTTP mapping. A failure remapped to `"degraded"` uses `onDegraded.httpStatus` or degraded defaults, not `onFail.httpStatus`. Custom rollups to `"ok"` or `"fail"` do not use degraded overrides.

## Output

`output` on the root config:

- **`format`**: `"json"` (default) or `"text"`.
  - JSON: `Content-Type: application/json`, body is `JSON.stringify` of `HealthResponse`.
  - Text: `Content-Type: text/plain`, human-readable lines (`status:`, then each check with latency and optional error).
- **`exposeError`**: Default **true**. If **false**, the `error` field is omitted from each check in the payload.

## Public API overview

**Runtime**

- `createHealthKit(config)` → `HealthKit`
- `HealthKit`: `start()`, `stop()`, `beginDrain()`, `handleRequest(req)`, `handleLiveness()`, `handleReadiness()`, `handleStartup()`
- `toFetchResponse(res, method?)` → Fetch `Response` (`HEAD` omits the body)
- `createFetchHandler(kit)` → `(request: Request) => Promise<Response>` for Deno, Bun, and Workers

**Types**

- `HealthkitConfig`, `CheckConfig`, `HealthAdapter`, `AdapterResult`, `CheckResult`, `HealthResponse`
- `CheckStatus`, `CheckType`, `RollupConfig`, `OutputConfig`, `DefaultsConfig`
- `AgnosticRequest`, `AgnosticResponse`

The canonical type definitions and any future additions live in the `healthzkit` package under `packages/healthzkit` in this monorepo.

## Startup and drain responses

Configure `type: ["startup"]` checks for `/healthz/startup`, or call `kit.handleStartup()` directly. Startup uses the same execution, cache, rollup, timeout, and output rules as liveness and readiness. Pending initialization is awaited until completion or timeout. Success is not latched: subsequent probes re-evaluate normally. With the default rollup, no matching checks returns 200 with empty `checks`; a custom rollup still determines the status. Startup does not automatically gate readiness; include initialization checks in both types when needed.

`handleRequest()` and `createFetchHandler()` recognize exact `{basePath}/live`, `{basePath}/ready`, and `{basePath}/startup` routes. GET and HEAD run the checks; HEAD omits the body. Other methods on these routes return 405 with `Allow: GET, HEAD` without running checks. Unknown paths return `null` from `handleRequest()` and 404 from the Fetch handler. The Fetch handler strips URL query strings.

`kit.beginDrain()` makes readiness return 503 immediately, with health status `fail` and empty `checks`. This overrides healthy cached checks, custom rollup, and custom HTTP mappings. Pending readiness requests also fail when their checks finish. Startup and liveness remain independent. See [Scheduling](/guide/scheduling#draining-and-restarts) for lifecycle behavior.
