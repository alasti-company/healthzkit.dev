---
title: Scheduling
description: Use Healthzkit scheduling to run slow dependency checks on an interval, spread replicas with optional jitter, and serve probes from a fresh cache.
---

For expensive checks (database, external APIs), run them on a timer and serve probes from cache.

<Note>
  Skip `kit.start()` on serverless platforms. Run checks on demand there, and use scheduling only in
  long-lived processes.
</Note>

```ts
const kit = createHealthKit({
  checks: [
    {
      name: "db",
      type: ["readiness"],
      adapter: { check: async () => ({ status: "ok" }) },
      schedule: { intervalMs: 30_000 },
    },
  ],
});

kit.start(); // starts background intervals for checks that define schedule
// ... on shutdown:
await kit.close();
```

## Timing validation

`timeout`, `defaults.timeout`, and `schedule.intervalMs` must be integer milliseconds from **1** to **2,147,483,647**, inclusive. Both `createHealthKit()` and `new HealthKit()` reject invalid values at construction with a `RangeError` identifying the field and, where applicable, the check name. Defaults are validated even if all checks override them.

`schedule.jitterMs`, when set, must be an integer from **0** through that check's `intervalMs`, inclusive. **0** selects a fixed interval, the same schedule as omitting `jitterMs`. A value above the interval, or a negative, fractional, or non-finite value, throws a `RangeError` naming the check and `schedule.jitterMs`.

Zero does not disable a timeout or interval. Zero, negative, fractional, non-finite, and oversized values are rejected instead of being coerced by runtime timers. Omit `timeout` to inherit `defaults.timeout` or **5,000ms**; omit `schedule` for on-demand checks. Timing settings are captured at construction; later mutations of the original defaults or schedule do not affect the kit.

## Behavior

- **`start()`** is idempotent; a second call does nothing.
- **`stop()`** clears intervals, pending jitter delays, and the cache.
- When a cached result is used, that check’s **`latency`** is **0** and **`cachedAt`** is an ISO timestamp on the check result.

Scheduled runs use the check's **`timeout`**, then **`defaults.timeout`**, then **5,000ms**. A timeout aborts the adapter context signal and replaces the cached result with a failure. Cancellation is cooperative: the adapter must use the signal with a driver or API that supports it (see [Deadlines and cancellation](/guide/checks-and-adapters#deadlines-and-cancellation)). Refreshes do not overlap: if an adapter remains pending after its timeout, later refreshes skip it until it settles. A late result cannot overwrite the timeout failure.

A cached success becomes a failure when its age reaches **`intervalMs + jitterMs + timeout`**. `jitterMs` is **0** when it is omitted, so the limit stays **`intervalMs + timeout`**. That window is one interval, the maximum jitter delay, and one refresh deadline. Healthzkit does not serve a cached success older than the limit. Failures follow your configured `onFail` behavior. While the initial scheduled check is pending, probes await that same check and share its result or timeout. If that run is still waiting for its initial jitter delay, the probe starts it immediately and then shares it. When scheduling is inactive and there is no cached result, probes run the check on demand with the same timeout.

Timers use `unref` when available so they do not keep the process alive by themselves.

## Jitter

Replicas that call `start()` together can run the same scheduled check at the same moments and burst traffic onto a dependency. Opt in per check:

```ts
schedule: { intervalMs: 30_000, jitterMs: 5_000 }
```

Omit `jitterMs`, or set it to **0**, and the first run starts immediately, then repeats every `intervalMs`. Healthzkit does not draw a random delay for that schedule.

When `jitterMs` is greater than 0, each initial run and each refresh draws a new uniform integer from **0** through **`jitterMs`** milliseconds, inclusive. The initial run waits only that delay. Each refresh waits **`intervalMs` plus a new draw**. After the first run, scheduled starts are at least `intervalMs` apart and at most **`intervalMs + jitterMs`** apart. `stop()` drops a delay that has not started a run. `start()` after `stop()` draws new delays. Checks draw independently.

Jitter only moves the start of a background run. The check deadline still begins when the adapter run starts, and it still lasts for the check's **`timeout`**, then **`defaults.timeout`**, then **5,000ms**. A probe does not wait out a remaining initial delay, so that response stays inside the check deadline. The freshness limit includes `jitterMs` so a refresh that uses the full extra delay can still finish inside its deadline. The deadline itself does not grow.

## Shutdown and disposal

```ts
// First stop accepting traffic and drain your application's requests.
// Then release resources created by health adapters:
await kit.close();
```

`stop()` only stops scheduling and clears cached results. You can restart scheduling or run checks on demand afterward. It does not dispose adapters. `close()` is terminal and immediately stops scheduling; every call returns the same promise, including after a cleanup failure.

Close waits for requests already accepted by the kit and for the underlying scheduled and on-demand adapter operations to settle. A check's response timeout does not end its underlying work. Close does not abort that work early or impose a shutdown deadline, so an adapter that never settles can keep close pending. Drain application traffic separately before closing.

Once close begins, `start()` throws `Error("HealthKit is closed")`. `handleLiveness()`, `handleReadiness()`, and matching `handleRequest()` calls reject with that error. Unmatched paths still return `null`; path matching remains available. Requests accepted before close retain their normal timeout and result handling; a pending scheduled result can report that scheduling was stopped.

Close calls each distinct adapter object's optional `dispose()` hook once, after pending work settles. Check-only custom adapters remain valid. All cleanup hooks are attempted even if another hook fails. Close rejects with an `AggregateError` whose `errors` array contains cleanup failures in adapter configuration order. Repeated close calls retain that rejection and do not retry cleanup. Check failures are reported through health responses, not added to cleanup errors.

Official adapters dispose only resources they create. Supplied clients, pools, connections, and their agents remain yours to close. Persistent drivers use their `end`, `close`, `quit`, `disconnect`, or `destroy` API as appropriate; checked-out pool connections are released before pool cleanup. AWS SDK v3 clients use `destroy()`. KafkaJS admin connections are disconnected after each check; disposal retries retained disconnect failures and reports any remaining errors. HTTP-based Upstash, AWS SDK v2, and MinIO clients have no client disposal API here; caller-provided HTTP agents remain caller-owned.

For official adapters that expose `dispose()`, direct users can call `await adapter.dispose?.()` for terminal, idempotent disposal that waits for active checks. Later direct checks return a failure without opening resources. Do not reuse a disposed adapter in another kit. Share an adapter across checks in the same kit only when those checks should share its resource lifetime.

For custom adapters, implement `dispose(): void | Promise<void>` to release only resources the adapter owns. Make it idempotent if the same adapter might be disposed directly or shared across kits. Do not await `kit.close()` from inside that kit's check or disposal hook, because close waits for those callbacks.

## Draining and restarts

```ts
// In your application's shutdown handler:
kit.beginDrain(); // readiness immediately returns 503
kit.stop(); // stop background intervals and clear cache
```

`beginDrain()` is idempotent and permanent for this kit instance. It does not stop scheduling, cancel pending checks, or change startup and liveness evaluation. Repeated `start()` and `stop()` calls are safe. `stop()` stops scheduling and clears the cache; probes remain usable on demand. `start()` restarts scheduling after `stop()` without resetting drain state. Create a new kit for a new application lifecycle. Your application owns process signals, HTTP shutdown, and adapter resources.

Startup checks can also be scheduled. Probes await the first scheduled run, then use the same cache freshness and refresh rules as other checks. Startup success is not latched by healthzkit; Kubernetes stops invoking its startup probe after success.
