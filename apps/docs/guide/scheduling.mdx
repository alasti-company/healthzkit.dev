---
title: Scheduling
description: Use Healthzkit scheduling to run slow dependency checks on an interval, serve probes from cache with low latency, and manage lifecycle with start, stop, and timestamps.
---

For expensive checks (database, external APIs), run them on a timer and serve probes from cache.

<Note>
  Skip `kit.start()` on serverless platforms. Run checks on demand there, and use scheduling only in
  long-lived processes.
</Note>

```ts
const kit = createHealthKit({
  checks: [
    {
      name: "db",
      type: ["readiness"],
      adapter: { check: async () => ({ status: "ok" }) },
      schedule: { intervalMs: 30_000 },
    },
  ],
});

kit.start(); // starts background intervals for checks that define schedule
// ... on shutdown:
kit.stop();
```

## Timing validation

`timeout`, `defaults.timeout`, and `schedule.intervalMs` must be integer milliseconds from **1** to **2,147,483,647**, inclusive. Both `createHealthKit()` and `new HealthKit()` reject invalid values at construction with a `RangeError` identifying the field and, where applicable, the check name. Defaults are validated even if all checks override them.

Zero does not disable a timeout or interval. Zero, negative, fractional, non-finite, and oversized values are rejected instead of being coerced by runtime timers. Omit `timeout` to inherit `defaults.timeout` or **5,000ms**; omit `schedule` for on-demand checks. Timing settings are captured at construction; later mutations of the original defaults or schedule do not affect the kit.

## Behavior

- **`start()`** is idempotent; a second call does nothing.
- **`stop()`** clears intervals and the cache.
- When a cached result is used, that check’s **`latency`** is **0** and **`cachedAt`** is an ISO timestamp on the check result.

Scheduled runs use the check's **`timeout`**, then **`defaults.timeout`**, then **5,000ms**. A timeout aborts the adapter context signal and replaces the cached result with a failure. Cancellation is cooperative: the adapter must use the signal with a driver or API that supports it (see [Deadlines and cancellation](/guide/checks-and-adapters#deadlines-and-cancellation)). Refreshes do not overlap: if an adapter remains pending after its timeout, later intervals skip it until it settles. A late result cannot overwrite the timeout failure.

A cached result becomes a failure when its age reaches **`intervalMs + timeout`**. This allows one interval plus the refresh timeout before a result becomes stale. Failures follow your configured `onFail` behavior. While the initial scheduled check is pending, probes await that same check and share its result or timeout. When scheduling is inactive and there is no cached result, probes run the check on demand with the same timeout.

Timers use `unref` when available so they do not keep the process alive by themselves.

## Draining and restarts

```ts
// In your application's shutdown handler:
kit.beginDrain(); // readiness immediately returns 503
kit.stop(); // stop background intervals and clear cache
```

`beginDrain()` is idempotent and permanent for this kit instance. It does not stop scheduling, cancel pending checks, or change startup and liveness evaluation. Repeated `start()` and `stop()` calls are safe. `stop()` only controls scheduling; probes still run on demand. `start()` restarts scheduling after `stop()` without resetting drain state. Create a new kit for a new application lifecycle. Your application owns process signals, HTTP shutdown, and adapter resources.

Startup checks can also be scheduled. Probes await the first scheduled run, then use the same cache freshness and refresh rules as other checks. Startup success is not latched by healthzkit; Kubernetes stops invoking its startup probe after success.
