The **healthzkit** npm package provides **liveness** and **readiness** probes without tying you to a specific HTTP framework. You implement small **adapters**; healthzkit runs checks in parallel, computes an overall status, maps it to an HTTP status code, and returns **JSON** or **plain text**. Optional **scheduling** runs checks on an interval and serves cached results on probe requests.

## Install

```bash
npm install healthzkit
```

The package is **ESM-only** (`"type": "module"`). The published entry is `./dist/index.mjs` (see the package `exports` field).

## Quick start

```ts
import { createHealthKit } from "healthzkit";

const kit = createHealthKit({
  checks: [
    {
      name: "db",
      type: ["readiness"],
      adapter: {
        check: async () => {
          // ping your database, etc.
          return { status: "ok" };
        },
      },
    },
    {
      name: "process",
      type: ["liveness"],
      adapter: { check: async () => ({ status: "ok" }) },
    },
  ],
});

// Wire into your HTTP server: path (+ optional method) from the incoming request
const res = await kit.handleRequest({ path: "/healthz/ready", method: "GET" });
if (res) {
  // res.status, res.headers, res.body
}
```

You can call `kit.handleLiveness()` or `kit.handleReadiness()` directly if your router already dispatches those endpoints.

## Routes and `basePath`

| Path               | Behavior                                        |
| ------------------ | ----------------------------------------------- |
| `{basePath}/live`  | Runs checks whose `type` includes `"liveness"`  |
| `{basePath}/ready` | Runs checks whose `type` includes `"readiness"` |

The default `basePath` is `/healthz`. Set `basePath` in config to change it (for example `/api/health` → `/api/health/live`).

`handleRequest(req)` returns **`null`** when `req.path` does not match either route, so you can delegate to healthzkit first and fall through to the rest of your app.

## Checks and adapters

Each check is a `CheckConfig`:

- **`name`** — Key in the response `checks` object.
- **`type`** — One or both of `"liveness"` and `"readiness"`. Only checks that include the probe type run for that probe. If none match, the response is still **200** with an empty `checks` object.
- **`adapter`** — Implements `HealthAdapter`: `check(): Promise<AdapterResult>`.
- **`timeout`** — Per-check timeout in milliseconds. Default **5000**, unless overridden by `defaults.timeout`.
- **`schedule`** — Optional `{ intervalMs }`. After `kit.start()`, the adapter runs on that interval and results are **cached** (see [Scheduling](#scheduling)).
- **`onFail`** — Optional `httpStatus`, `treatAs` (for example map `"fail"` to `"degraded"` in the payload and rollup while you tune HTTP behavior separately).
- **`onDegraded`** — Present on `CheckConfig` in TypeScript types only; **HTTP status** when the rolled-up status is `degraded` is controlled by **`defaults.onDegraded`** (see [HTTP status](#http-status)).

`AdapterResult` fields:

- **`status`**: `"ok" | "degraded" | "fail"`.
- **`error`**: Optional `Error` or string (included unless `output.exposeError` is `false`).
- **`metadata`**: Optional object copied into the check result.

If `adapter.check()` throws, the check is treated as **`fail`** and the error message is included when `exposeError` is true.

## Scheduling

Use background intervals for expensive checks (databases, external APIs) so probes read **cached** results:

```ts
const kit = createHealthKit({
  checks: [
    {
      name: "db",
      type: ["readiness"],
      adapter: { check: async () => ({ status: "ok" }) },
      schedule: { intervalMs: 30_000 },
    },
  ],
});

kit.start(); // starts intervals for checks that define schedule
// on shutdown:
kit.stop();
```

- **`start()`** is idempotent.
- **`stop()`** clears intervals and the cache.
- Cached results report **`latency: 0`** and **`cachedAt`** as an ISO timestamp on that check.

The scheduler invokes **`adapter.check()`** directly (no request-time timeout). If there is **no** cache yet, the probe path still runs the check **on demand** with the normal **timeout** behavior.

Timers call **`unref`** when available so they do not keep the process alive by themselves.

## Rollup status

Overall `HealthResponse.status` for a probe is:

1. Any **`fail`** → **`fail`** (unless remapped with `onFail.treatAs` on that check).
2. Else any **`degraded`** → **`degraded`**.
3. Else **`ok`**.

Override with `rollup.computeStatus(results)` for custom aggregation.

## HTTP status

The response **`status`** field (HTTP code) is derived as follows:

- Any check with **`status === "fail"`** and **`onFail.httpStatus`** set → that status code is used (**first** matching failed check in **config order** wins).
- Else if rollup is **`fail`**: `defaults.onFail.httpStatus` or **503**.
- Else if rollup is **`degraded`**: `defaults.onDegraded.httpStatus` or **200**.
- Else **200**.

`onFail.treatAs` changes per-check and rollup **logical** status in the body; combine with `onFail.httpStatus` or `defaults` when you need a specific HTTP code.

## Output

Root config **`output`**:

- **`format`**: `"json"` (default) or `"text"`.
  - JSON: `Content-Type: application/json`, body is `JSON.stringify` of `HealthResponse`.
  - Text: `Content-Type: text/plain`, lines for overall status and each check (latency and optional error).
- **`exposeError`**: Default **true**. If **false**, the `error` field is omitted from each check in the payload.

## Public API

**Runtime**

- `createHealthKit(config)` → `HealthKit`
- `HealthKit`: `start()`, `stop()`, `handleRequest(req)`, `handleLiveness()`, `handleReadiness()`

**Types**

- `HealthkitConfig`, `CheckConfig`, `HealthAdapter`, `AdapterResult`, `CheckResult`, `HealthResponse`
- `CheckStatus`, `CheckType`, `RollupConfig`, `OutputConfig`, `DefaultsConfig`
- `AgnosticRequest`, `AgnosticResponse`

`AgnosticResponse` is `{ status: number; headers: Record<string, string>; body: string }`, which maps cleanly to Express, Fastify, or a `Response` from the Fetch API.
